01  认识 WebAgent

是什么 · 在哪里 · 怎么定位

好，我们进入第一部分：认识 WebAgent。 这部分会回答三个问题：WebAgent 是什么？它在整个架构中处于什么位置？它和我们熟悉的传统代理有什么区别？

MCP 协议概览

Model Context Protocol (MCP) 是 Anthropic 提出的开放协议，
定义了 AI 模型 / Agent 与外部工具、资源的标准化交互方式。
在讲 WebAgent 之前，先快速过一下 MCP 协议。 MCP，全称 Model Context Protocol，是 Anthropic 提出的一个开放协议。 它定义了 AI 模型或 Agent 与外部工具和资源之间的标准化交互方式。 简单来说，MCP 解决的是「AI 怎么调用外部能力」这个核心问题。 如图所示，整个链路是：AI/LLM 通过 MCP Client 发起请求，MCP Server 接收后调用具体的 Tools 或 Resources。 Client 和 Server 之间使用 JSON-RPC 2.0 进行双向通信。 理解了 MCP，我们就能更好地理解 WebAgent 在其中扮演的角色。

定义

WebAgent 是一个开源的 MCP 代理转发枢纽服务，
它让 AI 智能体（Agent）能够通过 MCP 协议 驱动和操控 Web 应用。

不是什么

不是一个 AI 模型
不是一个 HTTP 反向代理
不是一个消息队列

是什么

MCP 协议的中间枢纽
Agent ↔ App 的桥梁
会话管理 + 消息转发

那 WebAgent 到底是什么？我们先用排除法来理解。 它不是一个 AI 模型——它本身不做推理和决策； 它不是一个 HTTP 反向代理——它不是简单地转发网络流量； 它也不是一个消息队列——它不做消息的持久化和削峰。 那它是什么呢？WebAgent 是一个 MCP 协议的中间枢纽服务。 它的核心职责是：在 AI Agent 和业务应用之间架起一座桥梁， 通过会话管理和消息转发，让 AI 能够通过标准的 MCP 协议来驱动和操控 Web 应用。 这是一个开源项目，大家可以在 GitHub 上找到。

WebAgent 提供四大核心能力。 第一，MCP 代理转发。它支持 SSE 和 Streamable HTTP 双传输模式，能完整代理 MCP 协议的所有消息类型。 第二，会话管理。每个连接的业务应用和控制端都有独立的会话，支持远程控制和调试。 第三，多协议支持。SSE、Streamable HTTP、WebSocket 三种传输层可选，适配不同的部署场景和网络环境。 第四，生产就绪。开箱即用的健康检查、Helmet 安全头、Winston 结构化日志、PM2 和 Docker 部署支持——这不是一个 Demo 项目，是可以直接上生产的。

OpenTiny NEXT 生态全景

来看看 WebAgent 在整个 OpenTiny NEXT 生态中的位置。 左边是 @opentiny/next-sdk，它集成到业务应用中，负责注册 MCP 工具、暴露可操控的能力。 中间就是今天的主角 WebAgent，作为代理枢纽服务，管理会话和转发消息。 右边是 @opentiny/next-remoter，提供操控端的 UI 体验，连接到 WebAgent 后向业务应用发送指令。 这三个组件协同工作，构成了完整的 AI 驱动 Web 应用的基础设施。 注意箭头方向：SDK 主动连接 WebAgent，Remoter 也主动连接 WebAgent，WebAgent 是被动的枢纽角色。

02  核心工作机制

引擎原理解析

接下来进入第二部分，也是今天最硬核的部分——核心工作机制。 我会逐步拆解 WebAgent 内部的引擎原理，包括四层会话模型、Twin Client 模式、双向消息转发桥等关键设计。 理解了这些机制，你就能明白 WebAgent 为什么不是一个简单的消息转发器，而是一个精心设计的协议代理。

四层会话模型

内部维护四组会话注册表

WebAgent 内部维护了四组会话注册表，构成了它的四层会话模型。 第一层是 Transports——底层传输连接，SSE、Streamable HTTP 或 WebSocket，负责实际的字节传输。 第二层是 Clients——业务应用会话，每个连入的业务应用在这里有一个 Twin Client 实例。 第三层是 Remoters——控制端会话，每个连入的 AI Agent 或控制端在这里有一个 McpServer 实例。 第四层是 Inspectors——检查器传输层，用于控制端的 Transport 管理。 这四层各司其职：Transports 管连接，Clients 管被控端，Remoters 管控制端，Inspectors 管控制端的底层传输。 每个连入的应用都有独立的 Session，互不干扰。

核心创新：Twin Client（孪生客户端）

WebAgent 不是简单地转发 HTTP 请求，
而是为每个连入的业务应用创建一个 MCP Client 实例（孪生客户端），
拦截并代理所有 MCP 协议交互。
这是 WebAgent 最核心的创新——Twin Client，孪生客户端模式。 这个设计解决了一个关键问题：WebAgent 不能像 Nginx 那样简单地做 HTTP 请求转发，因为 MCP 协议是有状态的，需要维护完整的协议握手和能力声明。 它的做法是：当一个业务应用通过 SSE 或 Streamable HTTP 连入 WebAgent 时，WebAgent 不是简单地记录这个连接，而是为这个应用创建一个完整的 MCP Client 实例。 这个 Client 实例就叫做 Twin Client——孪生客户端。它和业务应用端是「对称」的：应用端认为自己连接的是一个真正的 MCP Server，而实际上是 WebAgent 内部的 Twin Client 在代理所有交互。 关键点在于：Twin Client 声明了所有 MCP 能力——tools、resources、prompts、sampling——它让应用认为自己连上了一个全功能的 MCP Server。 但实际上，Twin Client 并不真正处理这些请求，而是把它们转发给远端的控制方。这就是「协议透传而非本地处理」。

Twin Client 初始化过程

三步完成孪生客户端的注入式初始化

Twin Client 的初始化分三步，我称之为「注入式初始化」。 第一步：清空原有处理器。MCP SDK 默认会注册一些请求和通知处理器。Twin Client 首先把这些全部移除，为自定义逻辑腾出空间。 第二步：注入自定义 initialize 响应。这一步非常关键——Twin Client 会返回一个「全能力声明」，告诉连接的业务应用：我支持 tools、resources、prompts、sampling、elicitation 所有能力。这让应用认为自己连上了一个功能完整的 MCP Server。 第三步：挂载监听器系统。为请求、响应、通知分别注册监听器链。这里有个重要设计：支持多个 Remoter 同时挂载到同一个 Twin Client 上，也就是说多个 AI Agent 可以同时观察和操控同一个业务应用。 三步完成后，Twin Client 就准备好了，等待 Remoter 连入后建立消息桥。

双向消息转发桥

Remoter 连入后，建立 McpServer ⇄ Twin Client 的消息桥

当 Remoter 连入后，WebAgent 会建立一个双向消息转发桥。 正向流程很直观：Remoter 发起请求，比如 tools/call、tools/list、resources/read 等，代理 McpServer 拦截后路由分发，最终由 Twin Client 转发给业务应用。业务应用处理完后，结果沿着反方向传回。 但这个桥是双向的——还有一个反向通道。 业务应用也可以主动向 Remoter 发起请求，典型的比如 roots/list（请求 AI 端提供根资源列表）或 sampling/createMessage（让 AI 生成消息）。 这种双向能力意味着 WebAgent 不仅仅是一个「AI 控制应用」的单向管道，而是一个真正的协议级双向桥梁。

一次 tools/call 的完整旅程

我们用一次完整的 tools/call 调用来串联整个流程。 Step 1：Remoter（也就是 AI Agent）发起 tools/call 请求。 Step 2：WebAgent 内部的代理 McpServer 拦截这个请求。 Step 3：McpServer 按 method 名称进行路由分发，识别出这是一个 tools/call。 Step 4：路由到对应的 Twin Client，调用 callTool() 方法。 Step 5：Twin Client 把请求通过 Transport 发送给实际的业务应用，业务应用执行工具逻辑。 Step 6：执行结果通过 Transport 回传到 Twin Client。 Step 7：McpServer 将结果封装为标准的 JSON-RPC 响应。 Step 8：Remoter 收到最终结果。 整个过程对 Remoter 来说完全透明——它以为自己直接在和业务应用通信，但实际上 WebAgent 在中间做了完整的协议代理。 这里的关键设计是：McpServer 的请求处理器被替换了，不再本地处理，而是路由给 Twin Client 的对应方法。

两种连接模式

WebAgent 支持两种连接模式，分别对应被控端和控制端。 左边是「应用接入」模式——业务应用不带 sessionId 连入 WebAgent。这时 WebAgent 会：创建 Transport、创建 Twin Client、注入处理器并完成连接、最后存入 clients 注册表。这个流程就是注册「我是一个可以被控制的应用」。 右边是「远程控制」模式——AI Agent 或控制端带着 sessionId 连入。WebAgent 会：查找对应的 Twin Client、为这个 Remoter 创建一个代理 McpServer、建立双向消息桥、最后存入 remoters 注册表。 区分这两种模式的关键就是 sessionId：不带 sessionId 的是应用接入，带 sessionId 的是远程控制。 这个设计非常优雅——同一个 API 端点，通过有没有 sessionId 来区分角色。

WebAgent 支持三种传输层，我们来看它们的差异。 SSE 模式：通过 GET 请求建立长连接，通过 POST 发送消息。会话用 URL 中的 sessionId 标识。浏览器兼容性最好，适合大多数 Web 应用场景。 Streamable HTTP 模式：每次 POST 请求携带 mcp-session-id Header。对 Serverless 环境特别友好，因为不需要维持长连接。初始化是在首次 POST 中检测 initialize 请求时触发的。 WebSocket 模式：全双工持久连接，延迟最低，适合需要频繁双向通信的场景。 但最重要的一点是：这三种传输层共享同一套 Twin Client + 消息转发机制。也就是说，不管你用哪种传输方式连入，上层的业务逻辑是完全一样的。传输层的选择只影响连接建立方式，不影响功能。

03  适用场景 & 不适用场景

找到正确的使用方式

了解了核心机制之后，我们来聊聊适用场景。 任何技术工具都有它的甜蜜区，也有不擅长的领域。正确使用 WebAgent 的前提是理解它适合做什么，不适合做什么。

适合的场景

  • AI 驱动的 Web 应用 — 通过自然语言操控前端界面、表单、数据展示
  • 企业 Agent 基础设施 — 多租户环境下的集中式 MCP 代理枢纽
  • 远程控制与监控 — AI / 运维人员远程操控应用状态、读取数据
  • 低代码 / 无代码平台 — Agent 驱动的自动化流程编排
  • 开发调试 — 通过控制端远程实时调试 MCP 工具注册和调用
WebAgent 最适合的场景有五类。 第一，AI 驱动的 Web 应用——这是最典型的场景，用户通过自然语言让 AI 来操控前端界面、填写表单、展示数据。 第二，企业 Agent 基础设施——在多租户环境下，WebAgent 可以作为集中式的 MCP 代理枢纽，统一管理所有应用和 Agent 的连接。 第三，远程控制与监控——运维人员或 AI 可以远程操控应用状态、读取运行时数据，非常适合运营和监控场景。 第四，低代码/无代码平台——Agent 驱动的自动化流程编排，让 AI 代替人完成拖拽、配置等操作。 第五，开发调试——在开发阶段，通过控制端实时调试 MCP 工具的注册和调用，大幅提升开发效率。

不适合的场景

  • 简单 HTTP 代理 — 如果不需要 MCP 协议，用 Nginx 即可
  • 高频消息队列 — 优化方向是 MCP 会话管理，不是高吞吐量
  • 纯同步批处理 — 以流式 / SSE 长连接为核心设计
  • 无 MCP 的 Agent — 依赖 MCP 协议，非 MCP 的 Agent 无法直接使用
同样重要的是了解不适合的场景。 如果你只需要简单的 HTTP 代理，不涉及 MCP 协议，用 Nginx 就够了，没必要引入 WebAgent。 如果你的场景是高频消息队列，需要高吞吐量，WebAgent 的优化方向是 MCP 会话管理，不是消息吞吐量，应该用 Kafka 或 RabbitMQ。 纯同步批处理也不适合——WebAgent 以流式和 SSE 长连接为核心设计，不适合批量的同步任务处理。 最后，如果你的 Agent 不支持 MCP 协议，就无法直接使用 WebAgent，需要先让 Agent 接入 MCP。

来看一个具体的场景：AI 操控电商后台。 假设运营人员对 AI 说：「帮我把 SKU-1234 的价格调整为 299 元」。 AI Agent 理解意图后，发起一个 tools/call 请求，调用 updatePrice 工具，传入 sku 和 price 参数。 这个请求到达 WebAgent，WebAgent 查找目标应用的 Twin Client，把请求转发过去。 电商后台（一个集成了 @opentiny/next-sdk 的 Vue 应用）收到请求后，执行 updatePrice 工具逻辑，修改数据库中的价格，然后返回操作结果。 整个过程中，运营人员只需要说一句话，AI 通过 MCP 协议和 WebAgent 完成了原本需要手动操作的任务。 这就是前端智能化的价值所在。

Step 1: 克隆与安装

# 克隆仓库
git clone https://github.com/opentiny/web-agent.git
cd web-agent

# 安装依赖（项目使用 pnpm）
pnpm install

# 复制环境变量
cp example.env .env

环境要求

Node.js ≥ 22  ·  pnpm ≥ 10

第一步，克隆和安装。 先从 GitHub 克隆仓库，然后用 pnpm install 安装依赖。 注意这里有两个环境要求：Node.js 22 以上，pnpm 10 以上。 安装完成后，复制 example.env 为 .env，根据需要修改配置——大多数情况下默认配置就可以直接使用。

Step 2: 启动服务

# 开发模式（热重载）
pnpm dev

# 或者生产模式
pnpm build && pnpm start

# 或者使用 Docker
pnpm docker:up
# 验证服务状态
curl http://localhost:3000/health

# 查看已连接的客户端
curl http://localhost:3000/api/v1/webmcp/list
第二步，启动服务。 开发模式下用 pnpm dev，支持热重载，改代码自动重启。 生产模式下先 pnpm build 编译 TypeScript，然后 pnpm start 启动。 也可以用 Docker——pnpm docker:up 一键启动。 服务启动后，可以用 curl 验证：访问 /health 端点检查服务状态，访问 /api/v1/webmcp/list 查看已连接的客户端列表。 如果返回正常响应，说明 WebAgent 已经成功运行了。

Step 3: 连接业务应用

// 在业务应用中集成 @opentiny/next-sdk
import { createMcpClient } from '@opentiny/next-sdk';

const client = createMcpClient({
  url: 'http://localhost:3000/api/v1/webmcp/mcp',
});

// 注册 MCP 工具
client.registerTool('getOrderList', async (params) => {
  return await fetchOrders(params);
});

await client.connect();
第三步，在业务应用中集成 SDK。 引入 @opentiny/next-sdk 的 createMcpClient 方法，传入 WebAgent 的地址创建客户端。 然后注册你的 MCP 工具——这里的例子是注册一个 getOrderList 工具，当 AI 调用这个工具时，会执行 fetchOrders 函数获取订单列表。 最后调用 client.connect() 连接到 WebAgent。 连接成功后，你的应用就在 WebAgent 的 clients 列表中注册了，等待 AI 端来操控。

Step 4: AI 端连接与操控

// AI 端 / Remoter 通过 Streamable HTTP 连接到特定客户端
const response = await fetch(
  'http://localhost:3000/api/v1/webmcp/mcp?sessionId=目标ID',
  {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      jsonrpc: '2.0',
      method: 'initialize',
      params: { ... }
    })
  }
);
第四步，AI 端连接与操控。 AI 端通过 Streamable HTTP 或 SSE 连接到 WebAgent，URL 中带上目标客户端的 sessionId。 连接时首先发送 initialize 请求完成 MCP 握手。 握手成功后，AI 就可以像使用普通 MCP Server 一样，调用目标应用注册的所有工具。 这里展示的是最原始的 HTTP 调用方式，实际使用中你可以用 MCP SDK 封装的客户端来简化代码。 至此，从克隆仓库到完成一次完整的 AI 操控 Web 应用的流程，就完成了。

核心 API 速查

端点 方法 功能
/api/v1/webmcp/mcp ALL Streamable HTTP 端点（推荐）
/api/v1/webmcp/sse GET SSE 连接
/api/v1/webmcp/messages POST SSE 消息转发
/api/v1/webmcp/list GET 所有客户端会话
/api/v1/webmcp/remoter GET 所有控制端会话
/api/v1/webmcp/tools GET 客户端注册的工具列表
/api/v1/webmcp/ping GET 健康检查 + 会话清理
/api/v1/webmcp/reset GET 重置所有连接
这是核心 API 的速查表，大家可以作为参考。 主要关注几个关键端点： /api/v1/webmcp/mcp 是 Streamable HTTP 端点，推荐优先使用。 /api/v1/webmcp/sse 和 /messages 是 SSE 模式的连接和消息端点。 /api/v1/webmcp/list 可以查看所有已连接的客户端。 /api/v1/webmcp/tools 可以查看客户端注册的工具列表，开发调试时非常有用。 还有 /ping 做健康检查和会话清理，/reset 可以重置所有连接。 这些 API 都是 RESTful 风格的，非常直观。

部署选项

PM2

pnpm build
pnpm pm2:start
pm2 logs web-agent

自动重启
内存阈值 1GB
优雅停机

Docker

cp example.env .env
docker compose up -d --build

多阶段构建
非 root 运行
健康检查

Nginx + PM2

proxy_buffering off;
proxy_read_timeout 86400;

SSE 需关闭缓冲
长超时配置

最后介绍三种部署方式。 第一种，PM2 部署：构建后用 PM2 启动，支持自动重启、内存阈值 1GB 告警、优雅停机。适合传统服务器部署。 第二种，Docker 部署：使用多阶段构建优化镜像体积，容器以非 root 用户运行，内置健康检查。适合容器化环境。 第三种，Nginx + PM2：生产环境推荐方案。但有一个特别需要注意的配置——因为 SSE 需要长连接，所以 Nginx 必须关闭 proxy_buffering，同时设置一个足够长的 proxy_read_timeout，比如 86400 秒（24 小时），否则 SSE 连接会被 Nginx 超时断开。 这三种方案大家可以根据自己的基础设施选择。
